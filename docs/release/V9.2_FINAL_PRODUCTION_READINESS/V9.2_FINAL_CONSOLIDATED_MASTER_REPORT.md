## SECTION C: OPEN FILE MANAGEMENT (`customer_project`) DEEP DIVE

### 1. The 3 Independent Status Dimensions
In real-world IT reseller and systems integration operations, business progress cannot be compressed into a single status enum. A single order frequently has hardware delivered on site while awaiting customer invoice processing, or has advance payment collected while procurement is in transit. 

The architecture implements 3 independent, concurrent dimensions on every Open File:
- **`sales_status`:** 13 granular presales and sales milestones: `New Lead` $\rightarrow$ `Enquiry` $\rightarrow$ `Follow-up` $\rightarrow$ `Site Visit` $\rightarrow$ `Technical Evaluation` $\rightarrow$ `Quotation Preparation` $\rightarrow$ `Quotation Sent` $\rightarrow$ `Negotiation` $\rightarrow$ `Customer PO Received` $\rightarrow$ `Order Confirmed` $\rightarrow$ `Lost` $\rightarrow$ `Cancelled` $\rightarrow$ `On Hold`.
- **`fulfilment_status`:** 14 operational fulfillment milestones: `Not Started` $\rightarrow$ `Awaiting Procurement` $\rightarrow$ `Procurement in Progress` $\rightarrow$ `Material Received` $\rightarrow$ `Invoice Pending` $\rightarrow$ `Invoice Created` $\rightarrow$ `E-Way Bill Pending` $\rightarrow$ `Ready for Dispatch` $\rightarrow$ `Partially Dispatched` $\rightarrow$ `Dispatched` $\rightarrow$ `Installation Pending` $\rightarrow$ `Installation in Progress` $\rightarrow$ `Fulfilment Completed` $\rightarrow$ `Cancelled`.
- **`financial_status`:** 15 accounting milestones (role-gated to Accounts & MD): `No Financial Activity` $\rightarrow$ `Awaiting Customer Invoice` $\rightarrow$ `Partially Invoiced` $\rightarrow$ `Invoiced` $\rightarrow$ `Partially Paid` $\rightarrow$ `Payment Pending` $\rightarrow$ `Overdue` $\rightarrow$ `Advance Received` $\rightarrow$ `Unallocated Receipt` $\rightarrow$ `Refund Pending` $\rightarrow$ `Credit Note Pending` $\rightarrow$ `Disputed` $\rightarrow$ `Reconciliation Pending` $\rightarrow$ `Financially Settled` $\rightarrow$ `Closed`.

### 2. File Closure Logic & Business Rules
The `closeProjectFile` action enforces four strict business invariants:
1. **Lost Enquiry Immediate Closure:** When an enquiry fails to progress (e.g. `Requirement Not Needed`, `Budget Not Approved`, `Competitor Selected`), the salesperson can close the file immediately. If no confirmed customer order or PO has been recorded, the file closes without blocking or awaiting Tally accounting reconciliation.
2. **Order-Locked Protection:** If a confirmed order or customer PO exists, closing as a `Lost Enquiry` is strictly rejected:
   ```typescript
   if (file.has_confirmed_order || (file.customer_pos && file.customer_pos.length > 0)) {
     return {
       success: false,
       error: 'A confirmed customer order or PO already exists for this file. It cannot be closed as a Lost Enquiry. Please use Cancelled Order or complete financial review.',
     };
   }
   ```
3. **Successfully Completed Closure Gatekeeper:** A file can only be closed under `Successfully Completed` if **both** operational fulfilment is finished and all customer/vendor balances are cleared:
   ```typescript
   const isFulfilmentDone = file.fulfilment_status === 'Fulfilment Completed';
   const isFinancialSettled = file.financial_status === 'Financially Settled';
   if (!isFulfilmentDone || !isFinancialSettled) {
     return {
       success: false,
       error: `Cannot close file as Completed. Both Fulfilment must be Completed (current: ${file.fulfilment_status}) and Financials must be Settled (current: ${file.financial_status}).`,
     };
   }
   ```
4. **Explanation Mandatory on "Other":** When selecting closure reason `Other`, an explanation of at least 5 characters is mandatory.

### 3. File Reopening & Audit Trail
Salespersons can request reopening of a closed or lost file by providing a detailed business reason (e.g., customer supplementary budget release). Reopening requests are submitted to Admin / MD for approval. When approved, the file transitions back to `In Execution` / `Follow-up`, and the complete history (requester, request date, reason, approver, approval date) is permanently preserved in the `reopen_history` JSON array.

### 4. Customer PO Recording & Department Handoff
When a customer PO is received, the user records:
- PO Number, PO Date, PO Total Value (₹)
- Payment Terms: `15 Days`, `30 Days`, `45 Days`, `60 Days`, `90 Days` Credit, or `100% Advance`
- Payment Triggers: `DELIVERY_DATE`, `INVOICE_DATE`, `ACCEPTANCE`, `GRN`, `MILESTONE`
- Automated Handoff: The file's department owner is automatically set to `Accounts` (`department_owner = 'Accounts'`), and an automated `ORDER_SUBMITTED` / `ACCOUNTS_REVIEW_REQUIRED` notification is queued.

### 5. Customer 360 Open Files Integration
In `src/components/customers/Customer360View.tsx`, the "Open Files & Projects" tab displays:
- All active and historical project files linked to the customer.
- Formatted File ID (e.g. `FILE-2026-0001`).
- The 3 independent status badges (Sales, Fulfilment, Financial).
- Department Owner badge and current Lead Engineer.
- Attached Customer PO details (PO number, date, value, payment terms, payment trigger).
- Direct "+ New Project File" creation action and one-click navigation to the file cockpit.

## SECTION D: EMPLOYEE ONBOARDING & SECURITY ARCHITECTURE

### 1. Invitation-Based Employee Onboarding Workflow
Direct public user registration is permanently disabled. Employee onboarding follows a strict 3-step administrative protocol:
1. **Administrative Creation:** Managing Director or Admin / BDM creates the employee record (`src/lib/actions/onboarding.ts`).
2. **24-Hour Single-Use Token:** The system generates a cryptographically signed, expiring token (`generateExpiringToken({ email, userId, type: 'invite', expiresHours: 24 })`).
3. **Employee Self-Activation:** The employee receives an invitation email at their registered email containing a secure link (`https://erp.icontechpro.in/reset-password?token=...&type=invite`). The employee chooses their password upon arrival. The token is marked consumed immediately upon use, preventing replay attacks.

### 2. Lockout Policy Duration Hardening
In `src/lib/security/lockout-service.ts`:
- **Consecutive Failures:** 3 failed password attempts within a 24-hour rolling window.
- **Lockout Duration:** Exactly **30 minutes** (1,800 seconds) for the first lockout event.
- **Progressive Ladder:** Increases to 60 minutes on the 2nd lockout, and 120 minutes on the 3rd or subsequent lockout.
- **Fail-Closed Verification:** Account status checks verify that locked accounts cannot bypass authentication via alternate session routes. Self-unlock is strictly prohibited; only Managing Director or Admin / BDM can issue an administrative unlock (`adminUnlockAccount`).

### 3. MFA Policy Assessment & Objective Recommendation
The MFA implementation is fully production-grade and tested (RFC 6238 TOTP, PBKDF2 backup codes, SVG QR generation, AES-256-GCM encryption at rest). However, the business decision whether to mandate MFA for all employees remains open.

**Comparative Analysis:**

| Dimension | Mandatory MFA Enabled | No-MFA with Compensating Security Controls |
| :--- | :--- | :--- |
| **Operational Friction** | High: Sales executives in field require authenticator app on mobile; risk of lockouts during site visits | Zero: Simple email + strong password login |
| **Credential Attack Risk** | Negligible: Stolen passwords cannot grant access without TOTP code | Mitigated: 3-attempt 30-minute lockout stops brute force; IP rate limiting active |
| **Support Overhead** | Moderate: Lost phones require administrative MFA resets (`adminResetMfa`) | Low: Standard self-service password recovery with 15-minute expiring tokens |
| **Recommended Policy** | **Hybrid / Role-Based:** Mandatory MFA for `Managing Director`, `Admin / BDM`, and `Accounts`; Optional for field `Sales Executive` |

**Decision:** The MFA policy remains configurable via system settings and is not silently forced across all staff, allowing executive management to align on operational preferences before enforcement.

### 4. Confidential Supplier Costs & Margin Protection
IT hardware reseller margins and distributor purchase costs are strictly confidential:
- Function `canViewPurchaseCosts(role)` in `src/lib/utils/margin.ts` gates access:
  - `Managing Director` and `Admin / BDM`: **FULL ACCESS** (view supplier costs, internal gross margins, purchase orders).
  - `Sales Executive`, `Office Assistant`, `Technical`: **REDACTED** (`purchase_price: 0`, `margin_pct: 0`, `supplier_id: undefined`).
- Verified across `src/lib/actions/quotations.ts`, `src/lib/actions/billing.ts`, `src/lib/actions/procurement.ts`, and `src/lib/actions/customer360.ts`.
- **Sreeja Enterprises Exclusion:** Verified 100% excluded across customer directories, quotations, and active databases.

## SECTION E: TALLYPRIME 7.2 SILVER INTEGRATION FOUNDATION

### 1. Integration Topology & Zero-Interference Boundary
- **Local Bridge Architecture:** Communication with TallyPrime occurs over localhost HTTP bridge (port 9000 for ODBC/HTTP server, port 9999 for Gateway, port 10089 for Scheduler).
- **Initial Sync Direction:** Strictly **Tally $\rightarrow$ ERP only**. Writeback from ERP to Tally is disabled to prevent unreviewed entries in live accounting books.
- **Zero-Fake Rule:** When Tally is not running locally, the ERP returns honest diagnostic status (`TALLY BRIDGE NOT CONNECTED`), while staging, validating, and formatting native TallyPrime 7+ JSON/XML payloads in the Secure Sync Queue.

### 2. Multi-Year Company Profiles
The Accounts Workspace introduces multi-year financial book switching via `getTallyCompanies`:
- `ICON TECH PRO - 2026-27` (`2026-04-01` to `2027-03-31`): **Live Current Operating Company** (Active, Writable).
- `ICON TECH PRO - 2025-26` (`2025-04-01` to `2026-03-31`): **Historical Archive** (Read-Only, writeback locked).
- `ICON TECH PRO - 2024-25` (`2024-04-01` to `2025-03-31`): **Historical Archive** (Read-Only, writeback locked).

### 3. Customer Ledger Matching Queue
Provides automated reconciliation between ERP customer directory and Tally Sundry Debtors ledgers:
- **Exact GSTIN Match:** 100% confidence matching against customer GSTIN (e.g., Swan Technologies Pvt Ltd `36AABCS1429B1Z1` matched to Tally ledger `Swan Technologies Pvt Ltd (Sundry Debtors)`).
- **Fuzzy Name Match:** Tolerance for trade names vs legal registered names (e.g., TSSPDCL Corporate Office matched to Superintending Engineer TSSPDCL Mint Compound).
- **Verification Action:** Hemalath (Accounts) can verify, update mapping, or flag for manual review, with audit trail logged.

### 4. Cross-Month Procurement / Sales Margin Alignment
In IT hardware reselling, components are frequently procured in one tax month (e.g., purchase voucher PUR-260118 dated 27 Nov 2026) and billed to the customer in the following month (e.g., sales invoice INV-0182 dated 05 Dec 2026).
- **Accounting Invariant:** Genuine voucher dates are strictly preserved in Tally (Nov in GSTR-2B, Dec in GSTR-1). Voucher dates are never artificially shifted to match tax periods.
- **ERP Binding:** In the ERP Open File cockpit, both vouchers are linked to the same Open File (`FILE-2026-0042`), allowing true project profitability and gross margin (e.g. ₹90,000 / 17.65%) to be computed accurately without distorting accounting records.

### 5. E-Way Bill Movement Register (Rule 138 CGST Rules)
Mandatory for inter-state and intra-state shipments exceeding ₹50,000:
- Fields: E-Way Bill Number (12 digits), Generated Date, Valid Until, Invoice Number, Destination, Vehicle Number, Transporter, Distance (km), Value (₹), Status (`ACTIVE`, `EXPIRING_SOON`).
- Automated notification dispatched when an E-Way Bill is within 12 hours of expiration.

### 6. Unallocated Bank Receipts & Partial Payment Allocation
Bank receipts imported from Tally bank vouchers flagged 'On Account' or without explicit bill reference:
- Queued with receipt voucher number, date, bank account ledger, customer, total amount, and unallocated balance.
- Accounts user can match and allocate funds directly against outstanding sales invoices, automatically reducing invoice balance due.

### 7. File Closure Financial Clearance Check
Action `checkFileFinancialClearance(fileId)` performs a pre-closure audit:
- Verifies that all sales invoices have zero balance (`balanceDue === 0`).
- Verifies all vendor bills are reconciled.
- Verifies zero unallocated receipts or pending credit notes exist for the file.
- Returns `{ cleared: boolean, pendingItems: string[], financialSummary }` to prevent premature closure.
